# RAG-Dagster

A RAG platform for PDF documents (text and tables): upload a document, choose how it is chunked, embed it into a vector database, and search it. A benchmark page compares embedding models, chunking strategies and search strategies (dense, hybrid, reranked) on one document and produces a PDF report.
Docling parses documents (read through LlamaIndex's `DoclingReader`), LlamaIndex splits them, Ollama embeds them, Qdrant stores and searches them (written through LlamaIndex's `QdrantVectorStore`), Streamlit is the UI, Dagster orchestrates the same pipeline for batch ingestion, and PostgreSQL keeps the metrics.

**Status: Phases 0 to 13 done.** The Docker stack (Qdrant, Postgres, Dagster, the Streamlit UI) runs. The UI has six pages: **Experiments** (above Upload: every experiment with the PDFs in it, and delete a PDF from an experiment or a whole experiment), **Upload** (upload a PDF, pick a chunking strategy and its settings, see where the cuts fall in the document, embed it into a new or existing experiment), **Try a query** (pick an experiment, a search strategy, set top k, search), **Chatbot** (ask questions of an experiment that has a BM25 vector; `gemma4:e4b-mlx` answers from the top chunks of a hybrid search with reranking, and the page shows each step, the thinking, the model state and the retrieved chunks) and **Database** (import CSV files into a schema of the database for imported tables, see what was imported, delete a table or a schema) and **Benchmark** (one document, every chosen embedding model x chunking strategy x search strategy, a saved report with a PDF download). A sensor registers PDFs in `data/raw/` as Dagster partitions and `ingest_job` runs parse, chunk, embed and index for one. `PLAN.md` holds the plan for the next phase, the ideas and the deferred items; `COMPLETED_PLAN.md` is the history of Phases 0 to 13 (Phases 6, 6a, 7 and 8 describe a benchmark dashboard, matrix runner and query set that Phase 11 removed). Update this file as phases land so that it describes what is actually in the repo.

## Architecture

```
upload / data/raw/*.pdf -> parse (Docling) -> chunk -> embed (Ollama) -> index (Qdrant) -> search
                                                                                |
                                                          metrics -> PostgreSQL (rag_metrics)
Benchmark page: one document -> an experiment per model x chunking strategy -> each search strategy over it -> probe and test queries -> report (+ PDF)
```

| Component | Where it runs | Address |
|---|---|---|
| Dagster webserver, daemon, code location | Docker on this Windows machine | http://localhost:3000 |
| Qdrant | Docker on this Windows machine | HTTP `6333` (dashboard at `/dashboard`), gRPC `6334` |

| Streamlit UI (Experiments, Upload, Try a query, Chatbot, Database, Benchmark) | Docker on this Windows machine | http://localhost:8501 |

Docling runs in-process inside the Dagster code-location container and inside the UI container (Upload and Benchmark parse there). This machine has no NVIDIA GPU, so everything local is CPU-only.

## Scope

- **In:** PDF documents; text and table content. CSV files imported into PostgreSQL, one schema per dataset (Database page).
- **Out for now:** image and figure ingestion, and OCR. Pictures are dropped at parse time, and picture and OCR features in Docling stay off (`do_ocr = False`) and are not exposed as config. Only PDFs with a text layer are supported. Do not add image handling or OCR unless asked.

## Working style

This project is kept minimal. Prefer the smallest change that works, and do not add code, config, abstractions or docs that nothing needs yet.

- **Few tests.** Write tests only for pure logic where a silent bug would corrupt results: retrieval metric formulas (Recall, MRR, nDCG), vector truncation and re-normalisation, config hashing, CSV import (cleaning of names, guessing of column types, delimiter detection: a silent bug there corrupts the data every later answer rests on) and the SQL guard (the one place where a silent bug is a security hole). No tests for Dagster assets, resources, Docling, Docker or anything needing Qdrant, Postgres or Ollama, and no mocks or fakes of them. Do not add test coverage to a change unless asked.
- **No re-testing after minor edits.** After a small change (rename, config tweak, comment, log line, doc edit, small refactor) do not run the test suite, rebuild containers or re-materialise assets. Run something only when a change alters the logic of one of the tested areas above, or when asked. Never rerun a passing check "to be sure".
- **Verify by running the real thing, once.** When a phase is finished, confirm it with a single real run (the "Done when" line in `PLAN.md`). Do not build extra verification around it.
- **Keep dependencies and services few.** Do not add a library, container or tool without a stated need in `PLAN.md`.

## Design rules

- **Every stage choice is a config value**, never a constant (Docling options, chunker, embedding dimension, distance metric). A new experiment is a new config, not a code edit.
- **Stages are modular.** Parsing, chunking, embedding, storage, search and the benchmark live in separate packages under `src/rag_lab/` as plain Python with no Dagster or Streamlit imports. Dagster assets in `assets/` and the pages in `ui/` are thin callers. Search must be usable without Dagster running.
- **One Qdrant collection per experiment.** The collection name comes from the experiment name, so runs with different settings never mix vectors. Each chunk also stores the config hash that produced it.
- **Vectors are supplied by us.** Qdrant only stores and searches vectors; embeddings come from the Ollama resource. Do not use the Qdrant client's built-in FastEmbed helpers for dense vectors.
- **Metrics go to PostgreSQL.** Ingestion stage metrics, the search log and benchmark reports are written to the `rag_metrics` database. Dagster asset metadata shows a summary of the ingestion numbers; Postgres is the source of truth.
- **Never write to the `dagster` database.** It belongs to Dagster. Our tables live only in `rag_metrics`; the user's imported tables live only in `rag_data`, which is written only by the loader role and read only by the reader role (see below).
- **Intermediates are kept on disk** under `data/artifacts/<experiment>/<stage>/` so that a stage can be re-run without redoing the ones before it.

## Key technical facts

- `qwen3-embedding:0.6b` outputs 1024-dimension vectors and supports smaller dimensions through Matryoshka truncation. Vectors must be L2-normalised again after truncation.
- Qwen3 embedding is asymmetric: **queries** get an instruction prefix (`Instruct: <task>\nQuery: <text>`), **documents** are embedded as-is. Mixing these up silently lowers retrieval quality.
- Tables are embedded as text (Markdown serialisation). Each chunk carries a `modality` of `text` or `table`.
- Chunking strategies are `hybrid`, `hierarchical`, `fixed`, `recursive` and `semantic`. `fixed`, `recursive` and `semantic` split text only and handle tables themselves by `table_handling`; `hybrid` and `hierarchical` are Docling's chunkers (Markdown table serialiser, `row-wise` unsupported). `overlap` applies to `fixed` only.
- `chunk.engine` is `llamaindex` (the default; `chunking/llamaindex.py`: `DoclingNodeParser`, `TokenTextSplitter`, `SentenceSplitter`, `SemanticSplitterNodeParser`) or `native` (our own splitters in `chunking/`, kept). `native` is left out of the config hash, so hashes of experiments made before the engine existed are unchanged, but a config that does not set `engine` is `llamaindex`. The `llamaindex` engine rejects `recursive.separators` and `semantic.breakpoint_type` other than `percentile`, ignores `semantic.min_tokens`, and takes the semantic threshold per section. `hybrid`, `hierarchical` and `recursive` give the same chunks as `native`; `fixed` and `semantic` do not (`semantic` made smaller chunks and scored lower on the one paper it was compared on).
- Embedding stays on our `OllamaEmbedder`; LlamaIndex only sees it through `embedding/llamaindex.py`, which the semantic splitter uses. LlamaIndex's sentence splitter downloads NLTK data on first use into `NLTK_DATA` (`/root/.cache/nltk_data`, the `model_cache` volume).
- `qdrant_index` writes with `QdrantVectorStore` into a collection that `QdrantStore.ensure_collection` created (unnamed vector, HNSW settings, payload indexes). The payload has the usual fields plus LlamaIndex's `_node_content`, `ref_doc_id` and `document_id`. Two runs of the same text can give embeddings that differ in the third decimal (Ollama), enough to move recall@5 by one query.
- `rag_lab/ingest.py` holds what the Dagster assets, the Upload page and the benchmark share: `save_upload`, `ensure_parsed`, `ingest_document` (parse and chunk files, experiment row, metric rows, embed, index), `embed_chunks`, `index_chunks`, `record_parse`, `record_chunk`, `register_experiment`, `check_new_experiment_name`, `experiments_with_settings`. The assets are wrappers.
- Uploads go to `data/uploads/<doc_id>/`, not `data/raw` (the sensor would register them), and are parsed once with default settings into `data/artifacts/_uploads/<doc_id>/`. The `ui` container mounts `./data` and `model_cache`.
- A document's id is the first 16 hex characters of the SHA-256 of its bytes; it is also the Dagster partition key. Renaming a PDF does not re-ingest it.
- Config identity: `ExperimentConfig.config_hash()` covers the settings and the optional `tag` (empty is left out, so older hashes are unchanged); `settings_hash()` ignores name and tag. The `experiments` row is keyed by `config_hash`, so two untagged experiments with identical settings share a row and the last name wins. The Upload page and the benchmark tag every experiment they create with its name, so each has its own hash. A Dagster run config for a tagged experiment must include `resources.experiment.config.tag` (the same value), or the assets would write under the untagged hash; the search CLI reads the stored settings by name and needs nothing.
- On Upload, an experiment can be a new one (any unused name) or an existing one with the same `settings_hash()`; several documents can share an experiment. An experiment that belongs to a benchmark report needs a confirmation before a document is added, and its report is not redone.
- Every `Chunk` has a `span` (`[start, end]` in `segment.reference_text(blocks)`, the document read in order) and `span_approx` (true for a split table or a paragraph Docling split); an empty span means no source text (an undecoded formula). The section strategies record exact spans; `chunking/spans.py` places the Docling chunkers' chunks by the `self_ref` of their items. Spans are only in `.chunks.jsonl`, not in the Qdrant payload.
- `rag_lab/library.py` lists what is in each experiment (documents and point counts read from Qdrant, with a scroll fallback for collections that have no `doc_id` index; also collections with no experiment row) and deletes a document or an experiment. Deleting goes Qdrant first, then files, then database rows, so it can be repeated after a failure. Deleting a document removes its points, its `parse`/`chunk`/`embed` files and its stage rows in that experiment; deleting an experiment removes its collection, folder and `experiments` row (stage rows, search log, chat sessions and chat turns go with it). It never touches `data/uploads/`, `data/raw/`, `data/artifacts/_uploads/`, `_cache` or anything in Dagster, and a folder is only removed for names that match the experiment name pattern.
- Benchmark (`rag_lab/benchmark/`): a report's rows are experiment x search strategy; `total_experiments` counts experiments. Each experiment's `benchmark_results.metrics` has `searches: {method: {search, quality, per_query, error}}` beside `chunking`, `embedding`, `index` and `snippet_coverage`; a result saved before search strategies (top-level `search`, `quality` and the `per_query` column) is read as `dense` by `runner.result_searches`. Rerank strategies are timed on the first `rerank_probe_count` probe queries in one pass; a failing method is recorded in its entry and does not fail the experiment. `runner.py` runs a report in a background thread of the UI process (one at a time), model by model, and saves each experiment's result to `benchmark_results` as it finishes; the report row (`benchmark_reports`) is heartbeated, and a `running` report whose `updated_at` is older than 15 minutes shows as `interrupted`. `report.py` builds the report as plain data that the page and `pdf.py` (reportlab, standard fonts, so Latin-1 only) both draw. Experiments are named `bench-<document>-<report id>-<model>-<strategy>`, tagged with their name, kept and searchable; a button deletes a report's experiments but keeps the report.
- **Search strategies** (`SearchConfig.method`, `search(..., options=, reranker=)`): `dense` (cosine, as before); `hybrid` (Qdrant `query_points` with two `Prefetch`es, dense and the sparse `bm25` vector, fused with RRF); `dense+rerank` and `hybrid+rerank` (the first stage fetches `candidates` hits, default 20, and the reranker keeps the best top k). They are query-time choices: `SearchConfig` is not part of `ExperimentConfig` or its hash, and all of them search the same collection. In the code the axis is `method`, because "strategy" means the chunking strategy. A hit's `similarity` is a cosine similarity only for `dense`; hybrid gives a rank-fusion score and the rerank methods the reranker's probability of "yes", so similarity spread is measured and shown for `dense` only.
- **Chatbot agent** (`rag_lab/agent/`, LangGraph and `langchain-ollama`; no Streamlit or Dagster imports): a fixed graph `condense -> retrieve -> grade -> generate`, with `grade -> rewrite -> retrieve` while the chunks do not answer it and `grade -> abstain` when the retries are used up. `condense` makes the question standalone from the last `history_turns` pairs (skipped without history; thinking off); `retrieve` is our own `search()` with `AgentConfig.search` (`hybrid+rerank`, reranker `dengcao/Qwen3-Reranker-4B:Q8_0`), not a LangChain retriever; `grade` judges the best chunk's reranker score: at or above `enough_score` (0.5) the chunks answer it, below `missing_score` (0.1) they do not, in between the model is asked yes or no (thinking off); `rewrite` (thinking off, at most `max_rewrites`, default 1) writes a different query and is shown the section titles of the closest chunks, because without them the 4B model invented words the document does not use; `abstain` is a fixed "not found" message listing the queries tried, with no model call; `generate` answers only from the numbered chunks, citing `[n]`, with the model's thinking on when `AgentConfig.think`, and is written for the standalone question, not the rewrite. The grading model is lenient: a stall-like question whose best chunk scored 0.385 (about a ditching) was judged answerable and got an off-topic answer. The thinking arrives in the reply's `additional_kwargs["reasoning_content"]`, the answer in `content`. `AgentConfig` (a `ChatModelConfig`, which holds what every flow shares: model, temperature, `num_ctx`, `think`, `keep_alive`, `history_turns`; model `gemma4:e4b-mlx` on the Ollama at `OLLAMA_BASE_URL`, `num_ctx` 8192 always set because Ollama's default silently cuts long prompts, `top_k`, `history_turns`) is not part of `ExperimentConfig` or its hash. It is a frozen Dagster config, so overrides go in the constructor. The experiment must have `index.sparse`, or the search raises. Every node reports what it does as typed events (`agent/events.py`: `StepStarted`, `StepFinished`, `Query`, `Graded`, `Rewrote`, `Retrieved`, `Thinking`, `AnswerToken`, `ModelState`, `Done`, which has `abstained`) through LangGraph's custom stream (`get_stream_writer`); the answer is read with `llm.stream`, so the thinking and the answer tokens are events too. `agent.run(graph, flow, question, history, metrics=, session_id=)` is the way to use a graph; the `flow` (a `DocumentsFlow` for documents) says what a saved turn needs (`kind`, `config_hash`, `cfg`, and `summarise(question, events, final)`, which returns a `Summary`: the last query, the hits, the answer, the citations and an optional extra write such as the search log), so the runner does not know what a chunk is. It it yields the events, ends with `Done` (answer, thinking, cited and unknown citation numbers, ms per step) and, given `metrics` and a `session_id`, saves the turn to `chat_turns` and the retrieval to `search_log`. A turn that fails is saved too, with `error` set (the step and the message) and an empty answer, before the error is raised again. A save that fails does not hide the answer: `Done.saved` is false and `Done.save_error` says why (the page shows it under the answer). `agent/events.py` has `to_dict` and `from_dict` to turn an event into JSON-able data and back, tagged by class name; `Retrieved` rebuilds its `Hit`s. `ModelState` is made in `agent/model.py:call_model`: whether Ollama already had the model loaded (`/api/ps`), prompt and output tokens (the usage is on the chunk that ends the generation, not the last chunk), tokens per second, and `context_full` when the prompt reached `num_ctx`. A chat is a row in `chat_sessions` (migration `0008`: `session_id`, `config_hash` of its experiment, `title` = the first question cut to 80 characters, `created_at`, `updated_at`), made by `MetricsStore.add_chat_turn` with the chat's first turn (not when a page opens) and touched by every later turn, in the same transaction as the turn. A chat has a `kind` for its whole life (migration `0009`): `documents` (the documents of an experiment, `config_hash` set) or `database` (later; no experiment). Every turn repeats it, under a composite foreign key `(session_id, kind)`, so the database refuses a turn of the other kind. `add_chat_turn` requires `kind`. `chat_turns` (migration `0007`, extended by `0008`) points at its session with `on delete cascade`, and both tables belong to the experiment, so deleting the experiment deletes its chats and their turns. A turn row has the question, the last query searched, the answer, the thinking, the final hits, `timings` (ms per step, summed over a retry), `model_states` and, from `0008`, `events` (every event of the turn except the token-by-token `Thinking` and `AnswerToken`, which `Done` makes redundant, so the turn can be replayed through the code that draws a live one), `abstained`, `cited`, `total_ms`, `settings` (the `AgentConfig` it ran with) and `error`. Rows from before `0008` have nulls in the new columns. The rerank time of a turn is in its `Retrieved` events, for example `jsonb_array_elements(events) e where e->>'type' = 'Retrieved'` and `e->>'rerank_ms'`. The Chatbot page (`ui/chat.py`, with `ui/trace_view.py` for `apply`, the rebuilding of saved turns and the "How this was answered" view; it is not called `trace.py` because that would shadow Python's own `trace` module) is a thin caller of `agent.run`: it lists only experiments with `index.sparse`, offers the installed models that report `completion` and `tools` (`data.chat_models()`, rerankers left out; the Thinking toggle is off for a model without `thinking`), fixes the search to `hybrid+rerank`, keeps the id of the chat in the URL (`?chat=<id>`, made on a first visit), so a refresh or a bookmark reopens it: the turns are read from `chat_turns` and drawn through the same `apply(trace, event)` that draws a live answer, from the saved `events` (a turn saved before `0008` is rebuilt from its columns: one search, no per-step verdict), and the selectors follow the chat's own source (see the next bullet); *New chat* starts another; a sidebar list of *Past chats* (the chats of both kinds, most recently used first, with an icon and the source in its tooltip) reopens one, source and all, and *Delete this chat* (a popover with a confirmation) deletes its `chat_sessions` row, whose turns go with it; the agent's history is derived from the displayed messages, not kept separately, so a reopened chat continues where it stopped; after each turn the page reruns to draw it from what was kept and refresh the list; draws the events live in an `st.status` (steps, rewritten query, found chunks, thinking) with the answer streaming below (a retry and the abstain notice show there too, and in the list of searches in the expander), and keeps a "How this was answered" expander (steps and times, model state, thinking, chunk cards with the cited ones marked) under every answer. A failed turn shows the step it failed in and is left out of the history. Chunk cards come from `ui/hits.py`, shared with Try a query.
- **BM25 sparse vectors:** `IndexConfig.sparse` (default false, left out of the config hash while false; the Upload page has a checkbox for it) makes `ensure_collection` add a named sparse vector `bm25` with Qdrant's IDF modifier, and `index_chunks` write it after the dense write (`QdrantStore.add_sparse`, `update_vectors` on the same point ids). The weights are our own BM25 term-frequency part (`embedding/sparse.py`: lower-cased `\w+` tokens hashed with crc32, `k1=1.2`, `b=0.75`, `avg_len` the mean of the document's chunks); queries are 1 per distinct token. For languages with spaces between words; others need a word segmenter. A collection made without `sparse` cannot be searched with `hybrid` (the search raises) and cannot take `sparse` later. LlamaIndex's `enable_hybrid` is not used: it renames the dense vector. The dense vector is the unnamed one (shown as `''` by the client) next to `bm25`.
- **Reranker:** Ollama has no rerank endpoint, so `reranking/ollama.py` sends one `/api/generate` call per (query, chunk) with the Qwen3-Reranker prompt, `raw: true`, one token and `logprobs`, and scores `P(yes)/(P(yes)+P(no))` (`yes_probability`). It needs an Ollama with `logprobs` (0.35 has it) and a build with a sharp yes/no: `dengcao/Qwen3-Reranker-4B:Q4_K_M` and `:Q8_0` work (`Q8_0`: P(yes) 0.999 for a relevant passage, 0.0 for an irrelevant one, about 1.5 s per pair when warm), while `dengcao/Qwen3-Reranker-0.6B` `Q8_0` gave a flat distribution (every token at `ln(1/vocab)`) and `F16` only weak scores; `pdurugyan/qwen3-reranker-0.6b-q8_0` is an embedding-style build that refuses `generate`. About 0.1 s per pair in the benchmark run (0.25 s in a cold first check), so 20 candidates cost 2 to 5 s per query. The pages list installed models whose name has `reranker` and that report the `completion` capability.
- Benchmark measurements: **probe queries** (sentences sampled evenly from the document, the same for every experiment) give latency and similarity spread, never quality. **Test queries** (a query plus a snippet that must appear in the right chunk, judged by `metrics/retrieval.py`) give hit rate, recall, precision, MRR, MAP and nDCG at 1, 3, 5, 10 up to top k, and **snippet coverage**: the share of snippets that appear whole inside some chunk, which caps what a chunker can score. Models are compared on speed and, with test queries, quality only: similarity scores are on a different scale for each model.
- `semantic` chunking calls Ollama for sentence embeddings (document mode, no query prefix). Limits are measured in tokens with the Qwen3 tokenizer, not characters. Semantic chunking caches sentence-group embeddings in `data/artifacts/_cache/embeddings/`, shared across experiments.
- Chunk sizes are counted with the Qwen3 Hugging Face tokenizer (`EmbedConfig.tokenizer`), cached in the `model_cache` volume. Headings are embedded with each chunk and use part of `max_tokens`.
- Use Ollama's `/api/embed` endpoint (batch input), not the older `/api/embeddings`.
- The Python client is `qdrant-client`. Search goes through `query_points`.
- With the cosine metric, Qdrant's `score` is the cosine similarity itself (higher is better). Report `similarity = score` and `distance = 1 - score`.
- Qdrant point IDs must be unsigned integers or UUIDs. Chunk IDs are turned into deterministic UUIDs (uuid5) so re-ingestion overwrites instead of duplicating.
- Filtering on a payload field (`doc_id`, `modality`, `source_file`) needs a payload index on that field; create them when the collection is created.
- Qdrant storage must be a Docker named volume. A bind mount to the Windows filesystem can corrupt its data.
- Ollama must be reachable from the containers at `OLLAMA_BASE_URL` (on a remote machine it must listen on all interfaces, `OLLAMA_HOST=0.0.0.0`; MagicDNS names may not resolve inside containers, so use the Tailscale IP).
- The code container takes about 50 s to start because it imports Docling. Reload the code location in the Dagster UI if it shows "could not reach user code server" right after `docker compose up`.
- The `model_cache` volume (mounted at `/root/.cache`) holds Docling's models. Ad hoc `uv pip install` in that container needs `UV_NO_CACHE=1`, or uv's cache (GBs) lands there too.
- Run config is set once per run on the shared `experiment` resource, not per asset: launchpad key `resources.experiment.config` with `name` (required) and optional `parse`, `chunk`, `embed`, `index`, `tag` sections. Assets read it with `experiment.config()`. Over GraphQL: `{"resources": {"experiment": {"config": {...}}}}`.
- Ingest end to end in Dagster: launch `ingest_job` for a partition with `resources.experiment.config` set. Changing `embed.dimension` needs a new experiment name, because a collection's vector size is fixed.
- A stage reads the previous stage's files from `data/artifacts/<experiment>/<stage>/`, so `chunks` needs `parsed_document` run first under the same experiment name (selecting both assets in one run does this).
- **The database for imported tables** (`rag_data`, in the same PostgreSQL; `rag_lab/sql/`): one PostgreSQL schema per dataset. `sql/bootstrap.py:ensure_database()` creates the database, the two roles and their limits if missing, as the admin role (the credentials in `METRICS_DATABASE_URL`, used for nothing else); it is idempotent (a second run changes nothing; a role's password is reset only when it cannot log in, so changing `SQL_*_PASSWORD` in `.env` takes effect) and runs when the UI starts (`ui/app.py` shows a warning, and carries on, if it fails) and by `python -m rag_lab.sql bootstrap`. The init script cannot do this for an existing volume. `rag_loader` may connect and create schemas and tables in `rag_data` and has a 10 minute statement timeout; `rag_reader` may only connect and `SELECT` from schemas it was granted, with `default_transaction_read_only`, `statement_timeout` 15 s, `idle_in_transaction_session_timeout` 30 s and a limit of 10 connections. `PUBLIC` has no rights on `rag_data` and none on its `public` schema. The roles' URLs are `SQL_LOADER_URL` and `SQL_READER_URL`, built by compose from `SQL_LOADER_PASSWORD` and `SQL_READER_PASSWORD` in `.env` (letters and digits only: they go into a URL). The grants are the boundary, not the read-only setting: a session can switch that off, and an `INSERT` then still fails with "permission denied for table". The reader can connect to `rag_metrics` and `dagster` (PostgreSQL lets `PUBLIC` connect, and changing those grants was left alone) but has no privilege on any table there, so it can see names in the catalogs and nothing else. `sql/database.py` has `create_schema` (as the loader: the schema, `USAGE` for the reader, and default privileges so every table the loader adds is readable; then the `db_schemas` row; a name already registered is refused) and `drop_schema` (the data first, then the registry rows, so it can be repeated; `db_tables` rows and the schema's chats go with it). Schema names follow the experiment name pattern, at most 63 bytes, and not `public`, `information_schema` or `pg_*`; generated SQL always quotes them. `db_schemas` and `db_tables` (migration `0010`) are in `rag_metrics` and cannot be foreign-keyed from `rag_data`, so they are kept in step by those two functions. `chat_sessions.schema_name` (a database chat) is a foreign key to `db_schemas` with cascade; a chat has an experiment or a schema, never both.
- **CSV import** (`sql/importer.py`, the Database page `ui/database.py`; settings in `ImportConfig`): `parse_sample` reads the first `sample_bytes` (4 MB) of a file: UTF-8 with or without a BOM (anything else is refused with a message to convert it), the delimiter (`,` `;` tab `|`, the one that splits the first lines into the same number of fields; not a comma just because decimals have one), the first row as the header, clean unique column names, and a type for each column from up to `sample_rows` (10,000) rows. `clean_identifier` lower-cases, turns anything that is not a letter, digit, mark or `_` into `_` (letters of any language and combining marks, so Thai works), prefixes a leading digit, avoids PostgreSQL's system column names and cuts at 63 bytes without splitting a character. `infer_type` gives `bigint`, `double precision`, `boolean` (`true` and `false` only), `date` and `timestamp`/`timestamptz` (ISO only; an offset on some values and not others is text) or `text`; a number with a leading zero, a digits-only value too long for a bigint, a thousands separator or `nan` is text, and an all-empty column is text. `import_csv` is one transaction as the loader role: create the table (`DROP` first with `replace`), `COPY ... FROM STDIN` the whole file, refuse a file over `max_rows` (1,000,000) or `max_bytes` (50 MB), and profile every column from the loaded data, so a bad row leaves nothing behind (a failed replace leaves the old table) and the error names the line (`COPY orders, line 3001, column total`). A table that exists is refused unless `replace`. The profile, kept in `db_tables.columns` with the column's type and `header` (the original header, also its first `description` when it differs from the name), is per column: nulls, distinct count, up to `sample_values` (10) example values for a text column with at most `max_distinct_for_samples` (50) distinct values, and the minimum and maximum of numbers and dates. A table imported again keeps the descriptions of columns with the same names. The CSV is kept at `data/csv/<schema>/<table>.csv` (git-ignored); `drop_table` removes the table, its copy and its registry row (the data first), `drop_schema` the whole schema, its folder and its rows. The registry row is written after the commit, so a failure there leaves an unregistered table that importing with replace repairs. The page cannot be driven in the app tester through `st.data_editor`, so the types shown are what an untouched editor returns.
- **The schema as the model sees it** (`sql/catalog.py`): there is no retrieval and no index; the model is given the whole schema. `render(metrics, schema)` builds one block of text from the registry (`db_schemas`, `db_tables`: the profile the import left, so it needs no query against the data): the schema's description, then for each table `Table schema.table: N rows. <description>` and a line per column with its type, its description, and, from the profile, `unique` (with up to three examples, which show the format of a code) or the example values (`values: ...` when they are all of them, `most common of N values: ...` when they are not) or `N distinct values`, the range of numbers and dates (a timestamp that is always midnight is shown as a date), and the NULL count. Names are quoted only when SQL needs it. Example values are cut at 40 characters, with quotes doubled. Between tables it lists **likely joins**: a column with the same name and type in two tables, when exactly one side is unique (a key and what refers to it) or its name is `id`, `key`, `code` or ends in `_id`, `_key`, `_code`, `_no`, `_number`; they are marked as guessed from names, since a CSV declares no foreign keys, and `status` in two tables or `name` unique in both is not one. `SqlAgentConfig.schema_char_budget` (12,000 characters, about 3,500 tokens; the other settings of the agent come with it) is checked by `SchemaText.check`, which raises `SchemaTooLarge` with the size and the number of tables instead of cutting the text. Descriptions are written on the Database page (a table's, each column's in the editor, the dataset's), saved by `MetricsStore.set_db_table_descriptions` and `set_db_schema_description`, and kept when a table is imported again. The page shows the size against the budget and the text itself.
- **The Chatbot page has two kinds of chat** (`ui/chat.py`, `ui/trace_view.py`): a new chat shows *Search in*, **Documents (vector database)** or **Database (tables)**, then the experiment or the schema (the radio keeps the last choice as its default, and both selectors are always visible and editable until the first question). The first question creates the chat with its kind and target; from then on the radio and the target are disabled with a note ("This chat searches ... Start a new chat to search somewhere else"), and the page takes the kind and target from the saved chat, not from what the page last held, so a stale page cannot change them: a documents turn aimed at a database chat is answered but refused by the database (the composite foreign key, `Done.saved` false with the constraint in `save_error`). A documents chat is built as before (reranker, top k, candidates); a database chat has the schema, the chat model and thinking, builds `SqlAgentConfig`, `agent.sql.build_graph` and a `SqlFlow`, and its history carries each answer's SQL (`history_of` uses `remembered`). The sidebar is built so the chat model is always offered, the reranker only for documents, and each kind explains what is missing (no experiment with a BM25 vector, no reranker, no schema). `apply()` folds the database events into `trace`: `schema` (`SchemaShown`, which carries the text the model saw), `sql_attempts` (each `SqlWritten` with its `SqlChecked` and `SqlRan`, and the database's error from `Repairing`), `sql` (the SQL that ran) and `standalone`. A database answer shows under it the SQL that ran in a code block (`show_answer(trace)`); one that could not be produced is the abstain notice with the last SQL and error. "How this was answered" for a database turn has the tabs *Steps and model*, *Thinking*, *Schema* (every table the model saw, the text itself) and *SQL and result* (every attempt's SQL, what was refused or what the database said, the SQL as it ran when the check wrote it out differently, and the result as a table, the first 100 rows). Live, the status panel names the step ("Reading the schema", "Writing the SQL", "Checking it", "Running it", "Fixing it") and shows each query and its verdict as it arrives; the thinking streams, the SQL arrives as `SqlWritten`. `MetricsStore.list_chat_sessions()` lists both kinds with their target; `get_chat_session` and `get_chat_turns` return the kind (and the schema).
- **Text-to-SQL agent** (`agent/sql/`, `SqlAgentConfig`, `python -m rag_lab.agent sql`): a graph `condense -> schema -> examples -> write_sql -> check -> run_sql -> answer`, with `check`/`run_sql` failing to `repair` (back to `check`) up to `max_repairs` (2) times and `schema`/`write_sql`/`repair` ending in `abstain` when the schema is over its budget or has no tables, the model replies `CANNOT`, or the repairs are used up (a fixed message with the reason, and the last SQL and error). `condense` rewrites a follow-up using the history, whose assistant entries end with `SQL used: ...` (`remembered()`), so "and only for Japan?" can be understood; `schema` renders the whole schema (`catalog.render`) and emits `SchemaShown`; `write_sql` and `repair` think when `think` is on, stream only the thinking (`call_model(tokens=False)`, because the SQL is not the answer) and emit `SqlWritten(sql, attempt)`; `check` runs the guard and then `EXPLAIN` as the reader, and emits `SqlChecked(ok, sql, reason)` with PostgreSQL's own message (which often says "Perhaps you meant ..."); `run_sql` emits `SqlRan` (columns, the first 100 rows, row count, whether cut, ms); `answer` (thinking off) is written from at most `answer_rows` (30) rows and states numbers as they are; zero rows is not repaired, the answer says nothing matched. `SqlAgentConfig`: temperature 0, `num_ctx` 16384, `schema_char_budget` 12,000, `max_repairs` 2, `row_limit` 200, `answer_rows` 30, `statement_timeout_s` 10, `use_examples` true, `examples_k` 3, `examples_min_score` 0.55 and an `embed` setting (`--no-examples` on the CLI turns the examples off). A saved turn has `kind = 'database'`, its chat has `schema_name` (no `config_hash`; `Flow.schema_name` and `add_chat_turn(schema_name=)` carry it), `query` is the SQL that ran (or the last one tried), `hits` is empty, `abstained` means no working query, and the rest is in `events`.
- **Good answers** (`sql/examples.py`, `sql_examples`, migration `0011`; the thumbs-up in the Chatbot, the *Good answers* section of the Database page, `python -m rag_lab.sql examples`): under a database answer whose SQL ran, a **Good answer** button keeps the question and its SQL as an example for similar questions; clicking it again (it shows as pressed, also after a refresh) removes it. A row of `sql_examples` has the schema (it goes with it), `question` as typed, `standalone` (what `condense` made of it, since "and for 2023?" means nothing alone), `sql`, `turn_id` (provenance, set to null when that chat is deleted, so the example outlives it), `enabled` and a unique index on the schema, the standalone question and the SQL, so the same pair is kept once (saving it again turns it on). **The SQL saved is what the model wrote for the query that ran** (`example_of(trace)` in `ui/trace_view.py`: the last attempt with a result), not the guard's rewritten form with its `LIMIT 201` and casts, so the model is not taught those. Each enabled example is one point in the Qdrant collection `sqlexamples__<schema>` (prefix `SQL_EXAMPLES_PREFIX`; `library.py` ignores it, or the Experiments page would list it as a collection without an experiment), made from the standalone question with the Ollama embedder (document mode; the query side has the instruction `SqlAgentConfig.embed.query_instruction`), our own vectors, cosine, with `embed_key` (`model|dimension`) in each payload so a point made with another setup is not matched (and a vector of another size raises, pointing at `--reindex`). Changes go **table first, then Qdrant**, so a failure between them is repaired by `reindex`, which rebuilds a schema's collection (every schema's without `--schema`) from the enabled rows; turning an example off deletes its point; `drop_schema(metrics, name, qdrant)` removes the collection with the schema, and `drop_schema` takes the stores first and the rows last. The agent's `examples` step (after `schema`) makes no call when the schema has no examples, else embeds the standalone question and takes up to `examples_k` examples at least `examples_min_score` similar (0.55: on six saved examples the best match of a probe scored 0.56 to 0.78 for a paraphrase or the same kind of question, 0.36 to 0.67 for another kind of question about the same table, 0.26 to 0.51 for an unrelated one, with qwen3-embedding:0.6b; the overlap is real, and the prompt calls them examples that "may not fit"), emits `ExamplesFound` (each: id, question, sql, score; an empty list means the schema has examples but none was similar enough) and puts them in the `write_sql` and `repair` prompts. The *Examples* tab of a database turn shows them. `run()` puts the saved turn's id on the final `Done.turn_id` (`add_chat_turn` returns it), which is how the page links an example to its turn; a replayed turn has it from its row. There is no login, so anyone's thumbs-up counts and a wrong one teaches the agent wrong SQL: the Database page lists a schema's examples with *Turn off* and *Delete*.
- **The SQL guard** (`sql/guard.py`, `sqlglot`, PostgreSQL dialect): `guard(sql, schema, tables, max_rows)` returns the SQL to run or raises `Refused` with a reason worded for the model. It accepts exactly one `SELECT` (with `WITH` and set operations), refuses any `INSERT`, `UPDATE`, `DELETE`, DDL, `SET`, `COPY`, `SELECT INTO`, locking clause or data-modifying CTE anywhere in it, refuses a function sqlglot does not know unless it is in `ANONYMOUS_ALLOWED` (which keeps out `pg_read_file`, `pg_sleep`, `set_config`, `nextval` and `query_to_xml`, which would run another query outside the schema check), refuses any table that is not in the chat's schema and in the catalog (a name is folded to lower case unless quoted; a CTE name is fine; `pg_catalog`, `information_schema` and other schemas are refused), qualifies every table with the schema, and adds a `LIMIT` or lowers one to `row_limit + 1` (so the executor can tell the result was cut; `FETCH FIRST n ROWS ONLY` is read as a limit, and `WITH TIES` or `PERCENT` is refused). **What runs is the SQL sqlglot writes out, not the model's text, and without comments**, so nothing the parser read as a comment or a string can reach the database as a statement; the rewrite also casts, for example, `AVG(double)` to a decimal so `ROUND(x, 2)` works in PostgreSQL. `sql/execute.py`: the reader role, `conn.read_only`, `SET LOCAL statement_timeout` and `search_path`, `explain()` (plans without running, so an unknown column or a type error is found first) and `run()` (reads at most `row_limit + 1` rows; values made JSON-safe). **Known limit: the guard is the only thing keeping one dataset from another.** The reader has `SELECT` on every managed schema, so a query that got past the guard could read another schema; the role stops writes, file reads and long queries, not that. Per-schema reader roles would close it (under Ideas).
- The Postgres init script that creates `rag_metrics` only runs when the data volume is first created. Schema changes go through new numbered files in `src/rag_lab/metrics/migrations/`, never by editing an applied one.
- `sqlalchemy<2.1` is pinned: SQLAlchemy 2.1 switches the default Postgres driver to psycopg 3, which breaks dagster-postgres.
- Running tests without a local `uv`: `docker compose run --rm --no-deps -e UV_NO_CACHE=1 -v ./tests:/app/tests dagster-code sh -c "uv pip install --system -q pytest && python -m pytest /app/tests -q"`. In Git Bash prefix it with `MSYS_NO_PATHCONV=1`.
- The search CLI loads an experiment's settings from the newest `rag_metrics.experiments` row with that name, so it only works for experiments that have been ingested at least through `chunks`.
- `rag_lab.search.quick.ask(query, experiment, top_k, modality, log)` is the notebook entry point. It runs on the host (not in a container), reads `.env`, maps `host.docker.internal` to `localhost` for Ollama, and reaches Postgres and Qdrant at `127.0.0.1` (`localhost` hangs on IPv6).
- The `ui` service uses the shared image, runs from `/app/ui` so it finds `ui/.streamlit/config.toml`, and bind-mounts `./src` and `./ui`. After editing a module other than the page scripts (for example `ui/style.py` or `ui/data.py`), restart it: `docker compose restart ui`. A new dependency needs `docker compose up -d --build`. Colours follow the dataviz palette validated for a dark surface (`ui/style.py`).
- Streamlit's app tester (`streamlit.testing.v1.AppTest`) can drive the pages, including uploads, but not `st.data_editor` (set its widget state through `session_state[key]`) or download buttons.

## Commands

```powershell
# the UI is at http://localhost:8501 (docker compose up -d)
docker compose up -d --build          # start the stack
docker compose logs -f dagster-code   # code location logs
docker compose down                   # stop; add -v to wipe Qdrant and Postgres volumes
docker compose exec postgres psql -U <user> -d rag_metrics   # inspect metrics
uv run pytest                         # the few pure-logic tests; no containers needed
uv run python -m rag_lab.search "query text" --experiment <name> --top-k 5   # needs OLLAMA_BASE_URL, QDRANT_URL, METRICS_DATABASE_URL
docker compose exec dagster-code python -m rag_lab.search "query text" --experiment <name>   # env already set
docker compose exec dagster-code python -m rag_lab.sql examples [--schema <name>] [--reindex]   # list the good answers saved for a schema, or rebuild their Qdrant collections from the table
docker compose exec dagster-code python -m rag_lab.sql schema --schema <name>   # print exactly what the text-to-SQL agent is given about a schema, with its size against the budget
docker compose exec dagster-code python -m rag_lab.sql bootstrap   # create the database for imported tables and its roles if missing (the UI does it at start-up)
docker compose exec dagster-code python -m rag_lab.agent sql "question" --schema <name>   # the text-to-SQL agent; no question = a chat loop; prints every step
docker compose exec dagster-code python -m rag_lab.agent documents "question" --experiment <name>   # chatbot agent for documents; no question = a chat loop; needs an experiment made with index.sparse
```

## Conventions

- Python 3.12, managed with `uv`. Ruff for lint and format.
- Config sections in `config.py` subclass `dagster.Config` (a pydantic model), so the same classes are the launchpad's run config. Plain pydantic models cannot be nested in Dagster config.
- Secrets and host addresses come from `.env`; never hard-code the Tailscale IP or database credentials.
- The host is Windows: use PowerShell syntax in docs and scripts, and forward slashes in paths inside containers.
